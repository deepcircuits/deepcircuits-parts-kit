# Contributing to the Parts Kit

Thank you for helping. The most useful thing you can send is a photograph of a real part that a drawing gets wrong: open a [drawing issue](https://github.com/deepcircuits/deepcircuits-parts-kit/issues/new?template=drawing.yml) with the photo and what differs. Bugs in the code go in a [bug report](https://github.com/deepcircuits/deepcircuits-parts-kit/issues/new?template=bug.yml).

Every part follows the rules in the [brand book](project/README.md). Read its first sections before you draw: the grid, the materials, the bench light, and *What ships*.

## The ground rules

- **Original art only.** Never copy another simulator's or vendor's board art, documentation drawings or logos. Draw from photographs, data sheets and measurements of the real part.
- **No logos or vendor names on a board.** Print what a board is (`UNO-CLASS`, `ESP32-C3`), never whose it is.
- **Pins on the pitch.** Every pin sits a whole number of 0.1-inch pitches from the first, and pins are named from the data sheet or the silk print in the printed order. A name that repeats is bare once and `.2`, `.3` after, never `.1`.
- **Names are frozen.** A published id, generator name, option name or pin name never changes meaning, and a rename keeps the old name working.
- **Nothing overlaps.** `check(artwork)` returns nothing for every drawing, in every state.

## Layout

| Path | What it is |
| --- | --- |
| `src/` | The generators as ES modules: `core` (tokens, primitives, pins, boards, chip, lens), the parts' modules (`passives`, `inputs`, `displays`, `pixels`, `symbols`, `sensors`, `modules`, `boards`, `actuators`, `breadboard` and `chips`: templates and the catalog parts built from them with their real pins and silk), `pieces` (the board pieces the families share: SMD parts, IC packages, header and pad rows, mount holes, USB ports, wire legs), `options` (every catalog generator's options as data), `catalog` (the catalog, its ids and the option checks, with no drawing code), `draw` (`drawPart` and `partPins`), `helpers` (turn, mirror, scope, encode), `dom` (patching a drawn part in a page), `element` (`<parts-kit-part>`), `elementControls` (how the element's input parts are pressed, dragged and keyed), `controls` (the knob, detent and dial geometry they are operated by), `check` (the overlap check) and `mount` (the preview helper). The entry points are `index.js` (the root), `templates.js`, `primitives.js`, `catalog.js`, `dom.js`, `element.js`, `controls.js`, `check.js`, `mount.js` and `families/*.js`. |
| `project/` | The brand book, `tokens.json`, a card for each generator in `generators/<Name>/` (its README and preview) and the README picture `assets/hero.svg`. `generators/index.d.ts` holds the types; `generators/catalog.d.ts` is generated from the options. |
| `images/` | Every catalog part as SVG files, with `manifest.json` and a README that shows them, generated by `images.mjs`. Committed so pages can link to the files; not in the npm package. |
| `docs/` | The documentation pages the README links to: pictures, the part element, drawing in code, the catalog and the API reference. |
| `index.html` | The gallery, generated by `gallery.mjs`. |
| `build.mjs` | Writes `src/tokens.js`, each entry point's `.d.ts`, `project/generators/catalog.d.ts`, `tokens.css` and `project/generators/bundle.js`. |
| `gallery.mjs` | Writes `index.html` and `project/assets/hero.svg`. |
| `images.mjs` | Writes `images/`: each part at rest, in its states, with its examples and in its colours. |
| `tokens-css.mjs`, `bin/parts-kit-tokens.mjs` | The tokens as CSS custom properties, and the command line that writes them. |
| `modules.mjs`, `catalog.mjs`, `options.mjs`, `element.mjs`, `suite.cjs`, `suite-previews.cjs`, `fuzz.cjs`, `inventory.cjs`, `standards.cjs`, `contrast.mjs` | The checks (below). |
| `tools/render.mjs`, `tools/render-suite.mjs` | Render parts to a PNG sheet with Playwright and print the overlap check for each. |

## Checks

Node 22 or newer, from the repository's root:

```bash
npm test               # the build, the gallery and every check below
node build.mjs         # src/ -> bundle.js, the .d.ts files, tokens.js, tokens.css
node gallery.mjs       # index.html and the README picture
node images.mjs        # images/: every part as SVG files, and manifest.json
node modules.mjs       # the ES modules and the bundle draw the same artwork; the vars mode moves nothing
node catalog.mjs       # every catalog part draws cleanly and every preset generator is listed
node options.mjs       # ids are their names' slugs; every option's default and examples draw as listed; pin names follow the convention
node element.mjs       # every option value, written as a <parts-kit-part> attribute, reads back as itself; every input part has a control
node suite.cjs         # the suite artworks: no overlaps (TOTAL 0)
node suite-previews.cjs
node fuzz.cjs          # random pin names, counts, finishes and sizes
node inventory.cjs     # every template carries the parts the real one has
node standards.cjs     # pins on the grid, legs, print and stroke sizes, against Fritzing's and KiCad's published rules
node contrast.mjs      # the brand book's contrast claims
```

The render tools need Playwright (`npm install`); `CHROMIUM_PATH` points them at a browser of your own. To see the gallery, serve the repository's root with any static server (`python -m http.server`) and open `index.html`.

## Changing a part

1. Find the generator (`grep -n "function <name>" src/*.js`) and change it. Pins go on whole pitches from the first pin; nothing may overlap, and `check(artwork)` says what does. A piece that more than one family draws belongs in `src/pieces.js`, so loading one family never loads another; esbuild bundles the modules.
2. Run `npm test`. `inventory.cjs` counts tagged elements per template, so a layout change usually means updating its row.
3. If the part has a card, update `project/generators/<Name>/README.md` and `preview.html`, and its measured row in the brand book.

## Adding a part

1. Build it from the nearest template (the brand book's *Families and templates*), or compose it from the primitives.
2. Export it from its module and from its family's entry point in `src/families/`, and type it in `project/generators/index.d.ts`.
3. Give a library part its row in `src/catalog.js` (an id that is its name's slug, a name, a family, the generator, the preset options that make it, and search terms) and its options in `src/options.js` (type, label, range or choices, default, and `state` for what changes while it runs). `options.mjs` fails until its family's entry point exports the generator and every option draws as its spec says.
4. Add a card in `project/generators/<Name>/` with a README that says what the consumer provides and a `preview.html` that mounts it in its states.
5. Run `npm test`, then record the change in the [changelog](CHANGELOG.md).

## Pull requests

Keep a pull request to one part or one change, and say what you measured the drawing from. The checks must pass. Generated files (`bundle.js`, the `.d.ts` files in `src/`, `project/generators/catalog.d.ts`, `src/tokens.js`, `tokens.css`, `index.html`, `project/assets/hero.svg`, `images/`) are committed; rebuild them rather than editing them.
